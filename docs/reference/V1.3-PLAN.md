# v1.3 — Plan de implementación

**Estado:** implementado (v1.3).

## Objetivo

Madurez financiera y de pareja: **ver tendencias en el tiempo**, **perseguir metas de ahorro**, **liquidar con flexibilidad** y **cerrar el ciclo** marcando pagos entre pareja.

El usuario debe poder responder:

1. *“¿Mis finanzas mejoran o empeoran en los últimos meses?”*
2. *“¿Cuánto me falta para mi fondo de emergencia?”*
3. *“Liquidamos 60/40 porque yo gano más — ¿cuánto toca?”*
4. *“¿Ya pagamos lo del mes pasado?”*

## Modelo de datos

### 1. `group_settings` (extensión de `groups` o tabla 1:1)

Opción recomendada — columnas en `groups`:

```sql
ALTER TABLE public.groups
  ADD COLUMN IF NOT EXISTS default_split_ratio NUMERIC(4, 3) NOT NULL DEFAULT 0.5
    CHECK (default_split_ratio > 0 AND default_split_ratio <= 1),
  ADD COLUMN IF NOT EXISTS split_mode TEXT NOT NULL DEFAULT 'fixed'
    CHECK (split_mode IN ('fixed', 'income_proportional'));
```

- `fixed`: usa `default_split_ratio` (0.5 = 50% cada uno).
- `income_proportional`: ratio = ingresos_usuario / (ingresos_usuario + ingresos_pareja) del mes en curso.

`transactions.split_ratio` ya existe — override por movimiento.

### 2. `savings_goals`

```sql
CREATE TABLE public.savings_goals (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  group_id UUID NOT NULL REFERENCES public.groups(id) ON DELETE CASCADE,
  user_id UUID NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  name TEXT NOT NULL,
  target_amount NUMERIC(12, 2) NOT NULL CHECK (target_amount > 0),
  -- Progreso: suma de txs en category_id opcional, o manual via current_amount
  category_id UUID REFERENCES public.categories(id) ON DELETE SET NULL,
  current_amount NUMERIC(12, 2) NOT NULL DEFAULT 0 CHECK (current_amount >= 0),
  deadline DATE,
  icon TEXT NOT NULL DEFAULT '🎯',
  is_completed BOOLEAN NOT NULL DEFAULT false,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

**Progreso**

- Si `category_id` set → `current_amount` = suma de aportes del usuario en esa categoría (mes actual o acumulado histórico — decidir en impl.: **acumulado histórico** recomendado para metas largas).
- Si no → `current_amount` editable manualmente (+ opcional sumar txs futuros).

### 3. `settlements`

```sql
CREATE TABLE public.settlements (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  group_id UUID NOT NULL REFERENCES public.groups(id) ON DELETE CASCADE,
  month DATE NOT NULL,
  from_user_id UUID NOT NULL REFERENCES auth.users(id),
  to_user_id UUID NOT NULL REFERENCES auth.users(id),
  amount NUMERIC(12, 2) NOT NULL CHECK (amount > 0),
  paid_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  note TEXT NOT NULL DEFAULT '',
  recorded_by UUID REFERENCES auth.users(id) ON DELETE SET NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_settlements_group_month ON public.settlements(group_id, month);
```

**Flujo**

1. Vista liquidación calcula deuda sugerida (como hoy).
2. Botón **“Marcar como pagado”** → insert en `settlements` con monto y mes.
3. Estado “Al día” si `settlementAmount < 0.01` **o** existe settlement del mes que cubre la deuda.
4. Historial: lista de settlements pasados (solo lectura + nota).

### Split proporcional a ingresos

```javascript
export function computeIncomeSplitRatio(myIncome, partnerIncome) {
  const total = myIncome + partnerIncome;
  if (total <= 0) return 0.5;
  return Math.round((myIncome / total) * 1000) / 1000;
}
```

## Riesgos y mitigaciones

| Riesgo | Mitigación |
|--------|------------|
| 6 queries de txs pesadas | Un fetch rango 6 meses + agrupar en cliente; optimizar después |
| Split proporcional cambia mid-mes | Congelar ratio al crear TX; recalcular solo nuevas |
| Metas vs categoría ahorro confusas | Copy: “Vincula a categoría o actualiza manualmente” |
| Settlement manual vs real transfer | Disclaimer: registro de acuerdo, no pago bancario |
| Dashboard saturado | Metas compactas; tendencia en `#informes` si hace falta |

---

## Criterios de aceptación

1. Usuario ve evolución de ingresos/gastos/ahorro en al menos 3 meses con datos.
2. Usuario crea una meta y ve progreso en dashboard.
3. Pareja configura split 60/40 (o proporcional) y liquidación refleja el ratio.
4. Usuario marca liquidación como pagada y aparece en historial.
